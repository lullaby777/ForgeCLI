日期：2026-11-16（Asia/Singapore）。本文件只记录和分析，未实现运行时改进。

已有工具新增等未提交改动包含在这个起点中，它不是未经修改的上游版本。
真实模型由用户手动调用；本次复核不调用模型。

## 数据真正支持什么

1. 原版在部分题上能写出通过独立验收的补丁，所以不能把改进目标简单定义为“再加一些写代码工具”。
2. 第 2、4 题因空回复在修改前结束，说明结束判定与消息协议处理有真实漏洞；不能归因为已经写了错误补丁。
3. 第 3、5 题功能通过但未最终总结，说明“补丁是否合格”和“执行为何结束/如何交付”要分别记录。
4. 续跑成功是探索证据：多了人工提示和预算，不能证明自动反馈本身有效。
5. 目前没有受控压缩或中断对照，不能声称上下文遗忘导致失败，也不能声称长任务状态方案已经有效。
6. 大量累计输入 token 与重复检查值得调查，但没有逐调用计时、压缩和缓存数据，不能直接判断浪费原因或量化可节省金额。

## 优先改进

### 第一批：异常响应、明确结束状态、执行记录

先独立修 ISSUE-001：区分正常最终文本、合法工具调用、异常空响应。
保存 finish_reason、逐次 usage、请求重试/错误、压缩事件、工具开始结束、代码改动指纹和停止原因。
finish_reason 缺失时记录未知，不推断正常停止。调用失败、输出长度不足、轮次耗尽应明确区分。
空回复不得作为任务完成证据，不能污染可恢复历史；旧历史修复须保留原始证据，并保证工具调用/结果配对。
合法 content=null + tool_calls 必须保留。仅模型请求的有限重试不得重放已经执行过的副作用工具。
用模拟流验证边界，不通过真实模型烧钱测试异常处理。

完成标准：异常空流不能记录成正常完成；旧问题会话可构造有效请求；达到上限能生成停止状态与当前产物说明；正常文本和工具循环不回归。

### 第二批：独立验证闭环与执行预算

保留 Agent 作为执行内核，在外部加 repair controller：修改一轮 → 程序验收 → 通过/反馈继续/明确停止。
模型停止调用工具只表示本轮结束，不代表任务成功。即使触及轮次上限，已有补丁也应验收，不机械丢弃。
固定原始测试与外部验收，验证指定代码指纹，记录退出码、超时和环境错误。
反馈应为最小必要失败信息，不提供参考补丁，不允许 Agent 修改验收标准。
明确总模型请求/修复轮次/时间等上限。费用依赖定价和完整 usage，未知时不能声称严格美元硬预算。
没有补丁、相同代码指纹和相同失败连续出现时，限制重复尝试并记录原因。

完成标准：已知好补丁通过、已知坏补丁失败；环境错误不当作代码错误；反馈后最多执行约定次数；无进展与预算耗尽均停止，保留失败证据。

### 第三批：最小可恢复任务状态

先存目标与约束、仓库起点/当前补丁指纹、执行状态、剩余预算、已验收事实、证据引用和下一步。
在完整工具批次/验收边界落盘，先支持正常暂停恢复，再考虑任意崩溃。
恢复先核对代码和环境，旧版本通过结果不能替当前版本背书；副作用结果未知不能盲目重放。
明确区别模型猜想和工具事实，长日志保存原文引用，不必第一版就做向量库或复杂记忆系统。

完成标准：暂停重启能继续；代码已变时旧证据失效；预算累计不清零；合法工具历史不被损坏。

### 第四批：受控评测和真正的长任务

五题保留为开发回归，不把已经修好的补丁合进原版基线。改进实验固定相同起点、模型配置、任务和总预算。
可比较 A 原版、B 响应/状态防护与记录、C B 加验证反馈；记录多种状态而非一个 pass/fail。
续跑实验额外比较“普通继续提示”与“具体验收反馈”，两边总预算相同，避免把更多计算误认为机制收益。
条件允许时重复运行，报告实际任务数与次数，不编造稳定提升。
再新增不参与调试的任务，单独做低上下文压缩、暂停恢复实验，评价通过率、约束违反、重复操作、token/时间与恢复表现。

## 暂不优先

更多模型适配、MCP/插件数量、复杂多 Agent 编排、桌面界面、检索记忆等不由本轮失败直接支持。
各题通过验收的业务补丁是独立任务产物，不能冒充新 harness 的原创贡献；合并之前应单独评审和做集成验证。
