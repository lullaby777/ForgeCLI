# 长任务检查点与恢复（第一版）

先读[项目主线与代码导览](项目主线与代码导览.md)，分清原有执行循环、共用验收能力与新增持久化调度器。本文侧重具体使用和恢复边界。

## 先理解使用方式

会话保存“聊过什么”，任务检查点保存“做到了哪、还欠什么、已经用了多少预算”。一份修复任务关联一个会话。
普通聊天的 /save、-r 行为继续支持；只有通过 /repair 或带 checkpoint_dir 的 --repair-config 创建的任务才启用完整恢复。
程序会自动保存关键节点，不需要不停手动 /save。退出后先恢复会话，再输入“继续任务”，由程序读取任务检查点，不把这四个字当成普通模型提示。

## 实际使用

需要运行当前主项目版本，并准备独立工作目录、本地 pytest 环境、可信验收脚本和位于工作目录外的配置文件。以下是后续真实使用方式；本次实现只跑模拟响应，没有执行真实模型。

```json
{
  "task": "修复指定问题，保留原有功能，不修改已有测试",
  "workspace": "/tmp/my-workspace",
  "checkpoint_dir": "/tmp/my-task-01",
  "verification": {
    "argv": ["/absolute/path/to/python", "/tmp/my-acceptance.py"],
    "protected_paths": ["tests", "/tmp/my-acceptance.py"]
  },
  "regression": {
    "argv": ["/absolute/path/to/python", "-m", "pytest", "tests", "-q", "--ignore=tests/test_live_smoke.py"]
  },
  "limits": {"max_model_calls": 30, "max_attempts": 3, "rounds_per_attempt": 10, "max_seconds": 900}
}
```

在当前 CoreCoder 交互界面输入 `/repair /absolute/path/task.json`。程序先创建检查点并保存关联会话，打印 `corecoder -r <会话ID>`，随后开始执行。
Ctrl+C 可以暂停正在执行的任务；若要关掉程序，回到输入提示后输入 quit。
下次重新启动 `corecoder -r <会话ID>`，看到任务进度后输入 `继续任务` 或 `/continue`。
`/sessions` 会标出关联任务的状态，`/task` 显示当前任务的阶段与已用预算。选择会话仍使用现有的 -r 参数，没有增加图形菜单。

也可以使用一次性入口：

```sh
corecoder --repair-config /absolute/path/task.json -p '修复指定问题' --yes
corecoder --resume-task /tmp/my-task-01 --yes
```

后一个命令读取同一个任务目录，不接受新的预算或任务参数；使用与创建时一致的模型、接口和运行时配置，密钥仍由当前环境提供。
--yes 表示用户显式自动授权工具；恢复不会从检查点自动恢复一次性权限批准。
任务会话禁用普通聊天、/compact、/model、/plan、/reset 等可能绕过预算或改变冻结配置的入口；普通聊天请另开会话。

## 具体代码分工

- corecoder/verification.py：两个调度器共用的本地验收、回归报告解析与基线比较；不决定重试和预算。
- corecoder/task_store.py：校验和、临时文件写入、fsync、原子替换、不可覆盖的基线文件及进程锁。
- corecoder/tasks.py：单任务状态机、原始基线、恢复核对、持久预算与双门禁。调用 verification.py 的独立检查器，以及 repair.py 的阶段反馈，不另写一套判分标准。
- corecoder/agent.py：在轮次开始、响应落入历史、工具批次准备/开始/结束时触发检查点回调。回调保存失败会阻止后续副作用。
- corecoder/session.py、cli.py：会话关联任务目录，识别“继续任务”，显示状态并进入程序恢复流程。
- corecoder/prompt.py：为任务使用固定工作目录，不因终端当前目录改变而错误更换任务环境。

## 保存的状态

state.json 保存任务编号、目标、固定配置、工作目录、原始代码指纹、保护文件指纹、模型及运行时身份、消息、待办清单、plan 状态、会话工作目录。
同时记录已用调用/尝试/轮数/活动时间、无进展计数及前次失败签名、当前阶段、检查输入指纹、反馈、进行中操作与结束原因。
接口已返回的 token 用量累计保存；取消请求或崩溃时未能确认的用量单独标记 unknown_usage_requests，不把未知账单冒充零。
不保存 API 密钥，不保存活线程、shell 进程或一次性工具授权。

baseline.json 在首次模型调用前生成，冻结原始回归测试标识、状态和失败清单，绑定原始代码与配置指纹，禁止覆盖。它不会随恢复重新生成。
临时文件写好并刷盘后才替换 state.json；损坏的记录直接拒绝恢复，不回退到预算更少的旧快照。
同一任务的进程锁覆盖整个执行过程，第二个进程不能同时继续并各领一份预算。锁随进程退出释放。

## 恢复时如何判断下一步

1. 读取并校验任务记录、配置和运行时身份，核对保护文件。原始基线缺失或损坏时停止，不从当前补丁重新建立失败豁免。
2. 恢复账本与消息。任务检查点是权威，旧会话里较旧的消息不会重置预算。
3. 核对当前代码。外部改动使旧检查失效，重新验证当前代码；原始失败基线、已用预算和无进展计数保持不变。
4. 安全中断后先验证已落盘代码，再决定继续模型执行。任务目标通过后还必须通过回归门禁。
5. 未变化的已完成任务直接展示结果，不重新调用模型。预算耗尽或达到停止规则时明确结束。

请求发出前先持久化占用次数；即使响应丢失也不退款。恢复途中同一次尝试剩余多少轮，就只执行剩余轮数；正常结束才转入下一次尝试。
上下文压缩也经过同一个模型入口计数，不单独获得预算。
正常暂停不计离线等待时间，但已执行时间保留。硬退出时，尚未结束操作的时长不确定，保守计入从开始到恢复的时间（含离线间隔，最多扣完剩余额度）；时钟倒退也不因此补充预算。
时间限制仍是调用边界的协作检查，不能保证即时取消已执行中的网络或自定义工具。

## 工具与检查中断的边界

工具调用前记录“即将执行”，完整结果进入消息历史后才清除标记。主 Agent 的并行工具批次作为整体记录；批次部分完成时不猜测每个操作的结果。
Ctrl+C 若发生在模型请求期间，调用已经计费占位，恢复后不会重放旧工具；若发生在一个已完整保存结果的安全节点，可继续检查与修复。
若工具执行开始但结果未完整保存，自动恢复停止为 tools_outcome_unknown；不因文件看起来正确或历史里补了 interrupted 回复就自动清除风险。
验收子进程在正常 Ctrl+C 时会被终止并等待，可在后续恢复时重新检查；硬退出留下的未确认检查则停止为 check_outcome_unknown，避免和可能仍在运行的进程重复执行。
第一版没有“强制清除未知标记”的命令，需要人工核对，后续再设计显式确认流程。不要手工编辑账本绕过。

## 范围

第一版覆盖本地 POSIX（macOS/Linux）、一个固定工作目录、单个主 Agent。任务模式移除子 Agent 工具，不支持并行子 Agent 的运行中恢复。
工作目录需要保留；文件指纹不等于代码备份，不支持直接搬目录或跨机器恢复。运行时代码或测试配置升级需要后续兼容迁移，不能直接忽略校验。
任务目录应位于工作区外；默认冻结 tests 目录，包括新增文件。需新增开发测试时，放在允许的位置或在任务开始前把保护范围配置为具体原有文件。
校验和与哈希防误改，不是对恶意进程的安全隔离，也不证明测试覆盖了所有错误。
本次未迁移或改写旧实验；旧 v4/续跑记录继续冻结。

## 如何离线验证

```sh
python -m pytest tests/test_task_recovery.py -q
python examples/task_recovery_demo.py /tmp/task-recovery-demo-01
```

演示使用固定响应和真实文件工具：先修目标却弄坏旧行为，模拟 Ctrl+C；新建 Agent 从检查点恢复，继承 2 次已用调用，修好回归后总调用为 4 次。
测试覆盖预算/尝试/轮数继承、原始失败不扩豁免、外部改动使旧检查失效、未知工具不重放、真实子进程 os._exit 后的请求记账、原子写失败、损坏记录、锁、时间/无进展计数及会话入口。
这些检查不会创建真实模型客户端，也不证明真实模型的修复成功率提升。
