# 项目现状与代码导览：验证修复结果，保留执行进度

本文对应当前主项目，以及截至本次整理已保存的实验记录。已完成本地检查器的小重构；预算、恢复和停止逻辑保持原样，没有调用真实模型或改变旧实验结果。

## 1. 项目现在到底做了什么

基础 CoreCoder 已有模型调用、文件/命令工具、上下文压缩与聊天保存。在这个基础上增加了两项工程能力：

- 代码修复验证闭环：用预先固定的本地检查判断代码是否合格，失败后带证据继续修，达到上限则如实停止。
- 长任务状态保留：把执行阶段、原始失败清单、预算和会话保存为检查点，程序重开后核对现场并接着执行。

两者共同组成一个本地修复任务执行器。前者决定“是否完成、下一步修什么”，后者决定“中断后从哪里继续、哪些事实仍有效”。
不是新训练的模型；也没有用第二个审查模型生成验收脚本。固定验收和回归是本地子进程，同一个修复 Agent 接收失败反馈。
当前实现并不等于高成功率的通用 Coding Agent，也不是已经完成的分布式任务平台。

## 2. 当前真实调用关系

持久化任务的主入口是 CLI 的 /repair、继续任务，或 --resume-task。

```text
cli.py：用户命令、会话选择
  └─ RepairTask（tasks.py）：当前持久化任务的调度者
       ├─ Agent.chat（agent.py）：模型 → 工具 → 模型
       ├─ VerificationRunner（verification.py）：本地验收、回归比较
       ├─ 反馈（repair.py）：根据失败证据生成下一条提示
       └─ task_store.py：可靠保存和读取检查点
session.py：保存聊天记录，以及它关联的任务目录
```

需要讲清一个当前的代码债务：

- RepairController.run 是较早的一次性、内存内修复调度器，仍服务旧 API 和不带 checkpoint_dir 的配置。
- RepairTask._execute 是后来增加的持久化调度器，负责阶段流转、暂停和恢复。
- RepairTask 不调用或创建 RepairController，直接使用独立的 VerificationRunner.verify/regress。RepairController 同样委托这个检查器；原私有方法保留为兼容适配层。
- 检查职责已经抽出，预算、重试和无进展判断仍有两套实现。这是后续待收敛的部分，本次没有改动。

阅读当前代码时先沿 RepairTask 这条主线，暂时不要同时对照两个 run 的全部细节。

## 3. 方向一：修复验证闭环

### 输入、处理、输出

输入：任务描述、候选工作区、固定验收命令、固定回归命令、保护路径与执行上限。

处理顺序：

```text
首次建立原始回归起点
→ Agent 修改候选代码
→ 目标验收
   ├─ 失败：根据执行事实生成反馈，有限续修
   └─ 通过：运行回归，与原始起点比较
             ├─ 有新增失败或丢失原有执行覆盖：反馈续修
             └─ 没有新增问题且保护检查合格：整体完成
```

每次恢复后若代码已落盘，会先检查当前代码，避免在已经修好时继续花模型调用。
Agent 的正常文本回复、空回复、轮数上限都不是整体完成证据。程序必须运行外部检查。

输出：整体完成与否、目标检查、回归结果、新增失败、退出原因、已用预算和原始日志。

### 先读哪些函数

1. `repair.py / VerificationSpec、RegressionSpec、RepairLimits`：看清任务开始前固定了哪些条件。
2. `verification.py / VerificationRunner.run_check`：只负责以 shell=False 启动本地命令，收集输出并处理超时。
3. `verification.py / VerificationRunner.regress`：读取 pytest JUnit 报告，按测试标识比较原始失败与当前失败，并检查原有测试是否消失或被跳过。
4. `repair.py / _recovery_feedback`：按“截断无修改”“修改但失败”“回归失败”等事实生成下一条提示。
5. `tasks.py / _check、_failure、_execute`：看检查结果如何决定下一步、如何停下。

核心判定可简化为“新增失败 = 当前失败集合 - 原始失败集合”。实际还检查报告有效性、测试覆盖是否丢失、保护文件及代码指纹，不能只做集合相减。

### 已经实现并验证

- 目标验收与回归两道门禁；原始失败在首次修改前冻结。
- 固定验收输入和报告校验；已有测试不能被修改、删掉或跳过来凑通过。
- 基于真实文件变化和检查证据分阶段反馈。
- 调用、时间、尝试、轮数与无进展上限；环境/报告异常单独停止。
- 空回复和输出截断有明确执行结果，历史空 assistant 消息清理是前置可靠性修复。
- 新增 24 项回归门禁测试；它们验证程序机制，不代表 24 个真实模型修复任务成功。

### 还缺什么

- 验收任务和标准仍需要人预先准备，不能自动理解任意用户需求并可靠判分。
- 任务集较小，尚未证明稳定成功率提升或稳定降低 token；阶段化反馈的独立贡献没有充分因果证据。
- 原有失败按测试标识识别，无法自动判定同一失败用例内部的失败原因是否变坏。
- 文件未变是当前无进展规则的主要信号，可能把有价值的调查也判成无进展，属于保守的止损策略。
- 代码指纹和保护检查防误改，不是安全沙箱；调用数也不是精确的计费上限。

## 4. 方向二：长任务状态保留

### 输入、处理、输出

输入：同一个任务目录，以及当前候选代码现场。恢复时不接受一份新的完整预算。

```text
读取 state.json 和原始 baseline.json
→ 核对记录、配置、运行时和保护文件
→ 恢复会话、待办与累计账本
→ 处理未决请求/工具
→ 代码变了则作废旧检查，重新验证
→ 从原阶段继续，或明确停止
```

会话保存“说过什么”，检查点保存“已经确认什么、还能做什么”。会话里旧的消息不能覆盖检查点里的账本。

### 先读哪些函数

1. `tasks.py / create`：定义任务、固定配置、创建初始账本。
2. `tasks.py / _save`：收集消息、待办、工作目录、文件指纹和累计时间。
3. `task_store.py / write_record、read_record、task_lock`：临时文件刷盘后原子替换，校验记录，防止两个进程同时推进同一任务。
4. `tasks.py / _model_call`：先持久化占用次数，再进入模型客户端；请求中断也不退回预算。
5. `agent.py / _checkpoint` 与调用位置：轮次、响应、工具批次边界触发保存。
6. `tasks.py / _run_locked`：加载检查点，核对基线和代码，处理未决操作，再进入 _execute。
7. `cli.py / _start_task、_continue_task` 与 `session.py / load_task_link`：把会话 ID 关联到任务目录，识别“继续任务”。

### 已经实现并验证

- 自动检查点、原始基线不可覆盖、会话关联任务、任务和执行阶段标识。
- 调用/尝试/轮数/累计时间/无进展账本继承；收到的 token 累计，未知用量单独标记。
- 代码外部变化时旧检查失效，已完成且代码未变时不再调用模型。
- 模型请求前持久记账；工具结果不明时阻止自动重放。
- 新增 29 项恢复测试，包含真实测试子进程直接退出、写盘失败、损坏记录、锁和 CLI 恢复。
- 最近一次完整主项目离线测试记录为 469 项通过，本轮整理未重新运行它们。

### 还缺什么

- 仅本地 POSIX、固定目录、单个主 Agent，不支持分布式恢复或运行中子 Agent 恢复。
- 未决工具目前会停住，没有外部结果查询、业务幂等去重或显式人工确认后的继续机制。
- 不支持搬目录、跨机器、运行时升级迁移；哈希不是代码备份。
- state.json 的 version=1 是格式版本，不是每次更新递增的乐观锁版本；本地并发采用 flock。
- 状态主要是字典和字符串，状态迁移约束隐含在控制流程中，还缺少更清楚的状态类型和恢复事件日志。
- 新任务创建后目标和配置冻结。没有自动识别用户补充/纠错/切题，也没有需求版本化或跨任务长期记忆。

## 5. 实验到底证明了什么

| 证据 | 能支持的结论 | 不能支持的结论 |
| --- | --- | --- |
| 最初五个修复任务 | 找到提前结束、交付不完整、目标与回归标准分离等问题 | 五题足以代表通用修复成功率 |
| 第四题 v3 | 两组有结果差异 | 阶段化反馈更好；两组当时都没实际消费反馈 |
| 第四题 v4 | 两种反馈都被消费，目标验收都通过；新增回归仍导致整体失败 | 阶段化反馈稳定提升整体成功率 |
| v4 失败现场续跑 | 自动识别文档引用回归并反馈，10 次新增调用后修好，两道检查合格 | 对复杂功能回归都能稳定修好 |
| 手动暂停恢复 | 同一任务和基线，暂停 7 次、打开会话仍 7 次，继续后累计 11 次 | 本次第四题修复成功；实际以 no_progress 停止，目标仍有 9 个失败 |

第一组证据是机制和行为验证，第二类关于模型质量、成功率、效率的结论仍需要独立的评测设计。
不要把所有迭代版本混成一组“成功率”；也不要把 469 个程序测试当成 469 个真实任务。

真实结果文件：
- `validation/continue-v4-results/分析报告.md`：剩余回归被反馈并修好的案例。
- `validation/manual-task-recovery-results/分析报告.md`：恢复正确但修复失败的案例。
- `validation/regression-gate/checks.json`、`validation/task-recovery/checks.json`：门禁和恢复的模拟测试记录。

## 6. 和用户提供文章的关系

参考原文：https://xiaolinnote.com/ai/agent/18_session_state.html 。本文只将其与本项目作概念对照，不把文章的完整能力视作本项目实现。
本项目属于任务状态与恢复这一类问题，采取本地文件和固定修复任务的具体实现。

| 对照项 | 本项目当前落点 | 边界 |
| --- | --- | --- |
| 目标与执行阶段 | task、config、phase | 固定目标和运行阶段，不是通用意图理解/子任务规划 |
| 未决操作 | pending、工具调用编号、消息结果 | 主 Agent 批次记录；未知即停止，没有业务级幂等查询 |
| 检查点与恢复 | state.json、baseline.json、运行时校验 | 本地固定目录，非分布式、非升级迁移 |
| 可信当前事实 | 文件指纹、检查输入、失败清单、ledger | 代码修复领域事实，未实现通用业务实体和长期记忆 |

不需要为了接近文章而先引入 Redis、向量库或更多 Agent。当前优先级是职责清晰、语义一致、自己能逐段解释。

## 7. 下一步怎么把代码收敛，而不是继续叠功能

第一步已完成，其余是后续待办，不能当作已有模块。

第一步已完成：公开的本地检查器 VerificationRunner。
verification.py 的 run_check、verify、regress 负责启动测试、读报告和比较基线。RepairTask 和旧入口都调用它；持久任务不再借用另一调度器的私有方法。
检查命令、失败语义、输出文件、旧接口与预算恢复逻辑保持不变，验证见 validation/verifier-refactor。

第二步：统一预算与恢复策略。
把累计账本、请求预占、停止判定整理成单一 BudgetLedger/StopPolicy；保存是其可选适配层，避免一次性和持久化路径各改一套。失败反馈也作为可独立测试的策略，而不继续塞进大循环。
这一步需要保留旧一次性 API 的兼容层，不能直接删掉旧入口或擅自重置旧格式状态。

第三步：改善状态可读性与日志。
明确 phase 是“做到哪里”、status 是“为什么停”、completed 是“是否通过全部门禁”。修正 no_progress 终态仍提示继续的文案，记录恢复开始、继承预算、基线校验、旧检查失效、恢复结束等事件。

第四步：等前三步读懂且离线测试稳定后，再设计评估。
先用固定响应和固定失败现场验证不变式。若后续要测反馈效果，固定相同代码、会话与失败证据，再只变反馈方式；不要继续从零反复跑第四题直到理想结果。

## 8. 阅读时只追一条真实轨迹

先追“改代码后回归失败”这一条：

`RepairTask._execute → Agent.chat → _check('acceptance') → _check('regression') → _failure → Agent.chat → 两关合格 → completed`

再追“暂停并恢复”这一条：

`_model_call 先记账 → 检查点保存 → Ctrl+C → paused → 会话关联同一任务目录 → _run_locked → 核对基线/账本/代码 → 检查或续修`

最后对照 test_regression_gate.py 的首个回归反馈测试，以及 test_task_recovery.py 的暂停恢复和未知工具测试。先弄清输入、状态变化、输出，再扩展到所有异常分支。

可以尝试自己解释以下五点，能解释出来再写进面试项目表述：
1. 为什么模型说完成，程序还要跑本地检查？
2. 为什么保留原始失败清单，而不是恢复时重新测一份当基线？
3. 为什么请求发出前就要保存调用次数？
4. 为什么未知工具结果宁可停止，也不能自动再执行一次？
5. 为什么本次“恢复正确但修复失败”是两个独立结论？

## 9. 基于当前证据可以怎样表述

“基于轻量 Coding Agent，我实现了任务验收和回归检查的修复闭环，并加入本地检查点恢复。完成由实际测试结果判定，失败时带证据有限续修；恢复时继承原始失败基线和执行预算，对结果不明的工具停止自动重放。我用模拟测试和真实手动案例验证了这些机制，目前范围是单机主 Agent，还没有证明普遍的修复成功率提升。”

这段表述是已有证据的边界。面试重点应是能解释设计和取舍，不需要声称算法创新或对标成熟产品的全面能力。
