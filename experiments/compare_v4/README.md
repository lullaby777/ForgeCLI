# 第四题 v4：为验收反馈预留执行机会

新目录 `/tmp/corecoder-compare-04`，正式任务从原始修复前代码开始，不继承 v3 的成功或失败补丁。
两组使用 v3 冻结且完全相同的 runtime。generic 沿用通用反馈原模板；staged 沿用阶段化反馈。
相对 v3 仅将每次尝试最多 30 轮改为 10 轮，另增加不改变请求或决策的观测字段。

统一条件：deepseek-flash、相同接口地址、温度 0、单次输出上限 8192、上下文配置 128000、请求超时 60 秒、SDK 自动重试关闭。
每次尝试最多 10 轮，总模型入口调用上限 30，最多 3 次尝试，执行上限 900 秒，中间验收上限 60 秒，最终回归上限 120 秒，连续两次无进展停止。
轮数与模型调用次数不是同一概念：空回复重试、压缩、子 Agent 等也可能占用共享调用预算，不保证一定能跑满三次。
执行期限在模型/工具边界检查，外层进程有硬超时；调用次数不是美元费用上限，模型入口内的 HTTP 重试行为沿用 v3。

## 手动运行

以下命令会调用真实模型，准备阶段不执行。使用终端中现有的有效 CORECODER_API_KEY，不把密钥写入脚本或截图。
没有密钥时可以在终端安全输入（zsh）：

```sh
read -rs 'CORECODER_API_KEY?API key: '; export CORECODER_API_KEY; echo
```

逐条运行，先通用组、后阶段化组；每组只跑一次，不追加人工提示、不手工修改代码：

```sh
/tmp/corecoder-compare-04/venv/bin/python /tmp/corecoder-compare-04/runner/run.py task04 generic --live
/tmp/corecoder-compare-04/venv/bin/python /tmp/corecoder-compare-04/runner/run.py task04 staged --live
```

任何目录下均可启动。程序自动执行修改、独立验收、失败反馈、有限续跑和最终回归。
已有 run 目录拒绝覆盖；缺密钥不会占用正式案例。中途退出或断网也保留现场，不在同一目录反复运行。
工具自动授权设置沿用 v3，任务仅限指定 workspace；该工作区不是安全隔离环境。

汇总不调用模型：

```sh
/tmp/corecoder-compare-04/venv/bin/python /tmp/corecoder-compare-04/runner/summary.py
```

## 看哪些结果

每组 `run/summary.json` 保存功能验收、回归、保护文件核对、执行停止原因、token 和耗时。
`run/feedback-usage.json` 和汇总中的 `feedback_usage` 分别记录：

- `feedback_generated_count`：生成了几份反馈。
- `feedback_submitted_count`：有几份被交给下一次 Agent 执行。
- `feedback_used_count`：有几份以最后一条用户消息的形式进入实际模型入口调用。
- `feedback_response_count`：其中有几份对应的调用收到了模型响应。
- `records`：每份反馈的来源尝试、请求编号、响应编号、下一次尝试调用数、文件有无变化、再次验收结果。

“被使用”这里只证明程序把反馈带入模型调用，不证明模型理解或采纳建议。请求报错时可以出现 used>0、response=0。
已提交却在调用前停止时 submitted>0、used=0。最后一次失败可能生成反馈但没有机会提交，不能算使用。
每次模型入口调用日志增加最后一条用户消息的哈希，用于匹配控制器生成的反馈；不额外发送提示，也不记录密钥。
如果进程被硬超时终止而未生成反馈汇总，应报告记录不完整，不能把缺失当作未使用。

只有两组确实消费反馈后，才有机会比较恢复行为；首次通过、无进展提前停止、预算耗尽都如实保留，不追跑到成功。
首个请求归一化哈希用于核对起点，不保证后续模型输出相同。各一次实验不能声称稳定成功率提升。

## 离线检查

正式案例只运行修复前外部验收，两组应各有 9 个失败/共 14 项；共同原始回归应为 352 通过、1 个已知 README 行数失败。
合成临时工作区用模拟响应检查六组流程：重复截断且无修改按无进展停止；持续修改但失败按 10+10+10 轮用尽上限；首轮失败、反馈后修复在第二次尝试通过。
同时测试“提交但没有模型请求”“请求出错没有响应”两种观测边界。离线测试不会调用真实模型，不消耗正式案例。
