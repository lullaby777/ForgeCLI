# 第四题 v2：8192 输出上限的对照结果

结论：两组均未产生代码修改，最终仍有 9 项验收失败。提高单次输出上限未使本次第四题得到修复。
控制器能检测并停止失败，但尚未将失败反馈转化为有效工具动作。

## 先解释 round_limit 与验收通过

工具调用会把修改写入磁盘。Agent 后续可能还在读文件、跑测试、检查边界，尚未给出最终总结就达到轮次上限。
Agent 停止不会自动撤销文件修改。外部启动器是另一个程序，随后可以对留下的文件执行测试。
因此“执行到达上限”和“最终代码通过测试”可以同时成立：前者描述控制流，后者描述产物。
第二题原版属于这种情况；不能仅根据 round_limit 判定修复失败，也不能把通过测试解释成模型已正常收尾。
本次第四题则不同：两组根本没有修改落盘，不能套用第二题的成功结论。

两轮都只有一次且输出配置已变化，不能将上述差异解释为稳定因果或宣称降本。

## 实际执行证据

- 原版：5 次入口调用，只读搜索；末尾空回复。最后一次报告输出 token 为 8192，但旧内核未保留 finish_reason，不能确认具体结束原因。
- 改进版第一次尝试：7 次调用，最后响应 finish_reason=length，completion_tokens=8192，has_text=false、tool_calls=0。
- 改进版第二次尝试：仅 1 次调用，再次 length、8192 输出、无正文/工具调用。
- 两次都没有代码变化，验收失败相同，故按 no_progress 停止，未耗尽总计 30 次调用或 900 秒预算。
- 改进版最大单请求输入 token 为 21,185，配置上下文上限 128,000；当前直接证据指向单次输出限制，没有上下文窗口耗尽的证据。
- 所有原有测试未改，两组回归均 352 通过、1 个已有 README 行数失败，没有新增回归。
- 首个规范化请求哈希相同，运行时/验收/测量脚本和模型设置与冻结清单一致。
- 本次独立重跑本地验收，结果仍相同，未追加真实模型调用；原始 v2、v1 结果与五个基线文件均保持不变。

## 第一版控制器的具体缺口

控制器记录了 output_limit 与代码未变，但生成下一轮提示时只使用“原任务 + 通用验收失败 + 输出尾部”。
实际第二轮用户反馈长 5056 字符，没有告知 output_limit，也没有明确告知没有产生代码修改。
因此系统虽然知道失败类型，却没有据此改变恢复策略。面对“尚未实施”和“已有补丁但测试失败”，给出的反馈基本相同。
更多断言失败堆栈不能代替明确的下一步动作。这是当前值得修改的工程点，不能把责任全部归于模型。

## 下一步如何改（本轮未实现）

1. 新增基于事实的恢复反馈分流：
   - output_limit 且无代码变化：说明上轮截断、无修改/工具动作；要求不要重复完整分析，下一步完成一个最小工具动作。
   - 已有修改但验收失败：反馈最关键的失败项目和必要输出。
   - 验收启动错误/超时：保留环境分类，避免当作补丁逻辑错误反复请求模型。
2. 压缩失败反馈：先给状态、代码是否变化、1—2 个核心失败，而非直接把 4000 字节堆栈当作主要指令。原始日志继续落盘。
3. 保存最小执行事实：实际读取成功的文件、当前代码指纹、已验证结果、未完成动作。模型猜想单列，不保存或重放内部推理原文。
4. 先用模拟响应测试反馈是否正确分流、截断工具是否仍禁止执行、已完成副作用是否不重放、无进展是否仍会停止。
5. 下一轮只比较“现有通用反馈”与“阶段化恢复反馈”，两边沿用 8192、同一模型和同一总预算。冻结旧 v2，不同时换模型、加记忆库或继续扩大输出上限。
6. 若阶段化反馈仍无动作，再单独研究模型调用配置/模型选择，不编造当前模型必然缺乏能力或新策略必然有效。

当前不能写“改进提高修复成功率”或“8192 解决截断”。可以写实的进展是：建立可复现对照，识别出输出截断与通用反馈不匹配的问题，下一步针对该失败类型做可验证策略。
