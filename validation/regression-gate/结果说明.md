# 回归检查接入修复闭环

修改位置：当前主项目的 corecoder/repair.py、corecoder/cli.py；增加 tests/test_regression_gate.py 和 examples/regression_repair_demo.py，更新流程说明及受源码变化影响的文档统计。未修改任何原有测试文件。

## 新流程

1. 配置固定的任务验收命令和回归命令。开始调用模型前运行回归，冻结原有测试的标识、状态和失败清单。
2. Agent 执行一次修复后先跑目标验收；目标未过时先反馈目标失败。
3. 目标通过后立即跑回归。新增失败、原有测试消失或被跳过都不能完成；生成 regression_failed 反馈，用例名与简短错误证据进入下一次 Agent 执行。
4. 再次修复后重新检查目标与回归；两关都通过且文件保护检查合格，才将 completed 记为 true。
5. 所有检查共用现有总时间、调用和尝试预算；连续无进展仍停止。预算不足、超时、报告异常和中断均保留原因与现场。

回归通过指“没有新增失败且没有丢失既有执行覆盖”，允许冻结起点的已有失败仍存在。失败清单只在模型执行前建立，不能把后续新增失败加入豁免。

## 接口与记录

RepairController 新增 regression=RegressionSpec(argv=...)；CLI 的 --repair-config 支持 regression 字段。固定命令使用 pytest 的 JUnit XML 报告，报告路径由控制器分配到工作区外。需要本地安装 pytest。

result.json 明确保存 completed、completion_scope、acceptance_status、regression_status、regression_baseline；每次尝试保存独立的 verification、regression、failed_phase、恢复反馈及是否提交给下一次执行。
完整回归输出保存为 regression-baseline.txt/xml 和 regression-N.txt/xml。只在目标验收通过后重复跑回归，避免每次目标仍错误时都跑全量测试。

兼容旧代码：未配置 regression 时保留旧 status=passed 接口，但 scope=acceptance_only、regression_status=not_configured、completed=false。整体交付必须使用带回归配置的入口并看 completed，不能把单独验收当作整体通过。

报告缺失、空报告、全部跳过、格式错误、重复标识、退出码不一致等不能算通过。自动保护根目录的测试收集配置；回归测试与外部脚本按 protected_paths 冻结。该机制防误改，不是操作系统级隔离，也不能证明测试覆盖了所有缺陷。

## 离线验证

- 完整离线测试：440 passed in 24.16s，明确排除 opt-in 的真实模型 smoke。
- 新增回归门禁测试：24 项，包括反馈后修复、原有失败保留、新增失败不可豁免、目标重新验收、预算与无进展、测试或收集配置被修改、环境异常、报告异常、真实子进程超时和检查过程改代码。
- 修改文件 lint 通过。
- 离线演示使用真实 WriteFileTool 和本地子进程：第一次修好目标但弄坏旧行为，目标通过/回归失败；第二次根据反馈恢复旧行为，目标与回归都通过，completed=true。两次脚本响应调用，真实模型调用为零。
- 五个基线、v1/v2/v3/v4 套件、baseline 和此前 validation 文件全部核对未变；原有测试文件哈希全部未变。

## 如何理解

回归失败就是“修好了这次的问题，却弄坏了原来能工作的东西或检查”。第四题的目标行为可以已经修好，整体交付仍不合格。

程序现在会在说完成前多做一道检查：原来的东西还好吗？发现新增问题，就带着具体错误交回同一个 Agent，给它有限机会继续修；全部合格才完成。
测试命令由人预先配置并固定，不由另一个大模型临时出题。模拟响应验证了这套程序流程，不能据此宣称真实模型修复成功率已经提升。

本次只做上述实现与离线验证，没有新建或运行下一轮真实模型对照实验。
