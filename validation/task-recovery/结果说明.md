# 长任务状态保留：第一版实现与验证

本次在主项目实现，未调用真实模型。完整离线测试 469 项通过（31.12 秒），新增恢复测试 29 项；修改文件 lint 通过。原有测试文件、五个基线、v1/v2/v3/v4、续跑副本以及此前结果逐项核对未变。

## 实现内容

task_store.py 提供校验和、刷盘、原子替换与任务进程锁。基线文件只允许首次创建，不覆盖；记录损坏时不回退旧账本，以免预算倒退。
tasks.py 提供 RepairTask.create 和同目录恢复。检查点保存目标、冻结配置、运行时身份、代码与保护文件指纹、原始回归起点、消息、待办、目录、检查阶段和预算账本。
Agent 在轮次、模型响应和工具批次边界保存状态；模型入口在实际请求前持久化占用次数，收到的用量随后累计，未知用量另作标记。
CLI 将任务关联到会话：/repair 开始，-r 选择原会话，“继续任务”或 /continue 恢复；/task 查看状态。也支持 --resume-task 路径直接恢复。

## 已验证的关键行为

- 软中断后恢复沿用调用、尝试、轮数、执行时间与无进展计数；不存在新领整份预算的分支。
- 原始失败清单保持冻结。当前补丁上的新失败不会在恢复时被加入豁免；基线丢失或损坏直接停止。
- 外部改动使旧检查失效，重新验收；已有测试、配置或运行时改变则拒绝自动恢复。
- 未变化的完成任务直接展示结果，不调用模型。安全节点已落盘的代码会先检查，再决定是否需要模型。
- 真实测试子进程在模型入口 os._exit(23)，父进程读到已经保存的请求占用；恢复后不退款，也不重放历史工具。
- 工具实际写过文件再模拟 Ctrl+C，恢复时停为 tools_outcome_unknown，没有再次执行工具。
- 硬退出留下未确认检查时停止；正常 Ctrl+C 会终止并等待本地检查进程，之后可以重新验证。
- 写入失败阻止模型派发；校验和错误、独占基线、任务锁以及会话链接均有测试。
- 普通聊天和 /compact 等不能在关联任务会话中绕过账本；会话消息不能重置任务进度。

## 完全离线演示

examples/task_recovery_demo.py 用真实文件工具和本地 pytest 检查：先修目标却弄坏旧行为，再模拟暂停；创建新 Agent 恢复同一任务，收到新增回归反馈后修好旧行为。
暂停时已用 2 次脚本响应入口，完成后累计 4 次、2 次尝试，completed=true，真实模型调用为零。输出见 demo-final.txt，检查点和报告见 offline-demo/。
该演示验证编排机制，不代表真实模型的成功率或成本提升。

## 使用与范围

完整配置与使用步骤见 docs/task-recovery.md。需要通过持久化任务入口启用；普通 /save 仍保存聊天记录及可选任务链接，不能把旧会话自动升级成完整任务检查点。
第一版仅支持本地 POSIX、固定工作目录、主 Agent；移除子 Agent 工具，暂不支持运行中子 Agent、跨机器/搬目录恢复或运行时升级迁移。
工具或硬退出检查结果不明时不自动重放，也没有自动清除未知标记的入口；需人工核对，后续再设计显式确认机制。哈希防误改，不是操作系统隔离。
正常暂停不扣离线时间；硬退出留下的未知操作时长保守计入，可能耗尽剩余时间。已有请求调用次数始终保留，未知响应不假装是零用量。

文件说明：full-final.txt 是最终完整测试；task-tests.txt、focused.txt 是开发中间阶段检查，最终新测试数量以全套结果和 source/tests/test_task_recovery.py 为准。checks.json 保存最终指标、来源哈希与保留核对结果。
