# 本地检查器小重构

本次仅将本地验收、回归报告解析和原始失败比较抽到 corecoder/verification.py 的 VerificationRunner。两个调度器共用这一实现，预算与恢复规则没有重新设计。

## 分工

- Agent：调用模型、执行代码工具。
- RepairController：保留一次性修复调度。
- RepairTask：保留持久化修复调度、账本与恢复。
- VerificationRunner：运行固定命令、处理单次检查超时、保留日志、解析 JUnit、比较原始失败与当前失败，返回证据。
- repair.py 的 _recovery_feedback：仍负责根据证据形成反馈，本次没有迁移。

检查器没有模型对象、不读模型预算、不决定下一轮修复、不创建任务检查点，也不会自动改写原始基线。传入的 timeout 由调度器依据原有预算规则计算。

## 沿持久化任务读一次流程

1. CLI 进入 RepairTask.run。恢复核对、已用预算和保护文件校验仍由原方法完成。
2. RepairTask 创建 VerificationRunner，传入工作区、固定命令和报告目录；不再创建另一个 RepairController。
3. 第一次任务需要建立起点时，_baseline → _check('baseline') → checker.regress(..., baseline=None)，得到原始测试与失败记录，再由 RepairTask 冻结保存。
4. _execute 调用 Agent.chat 修改文件。Agent 返回后，_check('acceptance') → checker.verify，检查目标问题。
5. 目标通过后，_check('regression') → checker.regress(..., 原始基线)，得到新增失败或通过结果。
6. 失败后的反馈与有限续修仍由 _failure 决定；全部合格时仍由 _execute 设置 completed=true。检查器只交卷面结果。

可简化理解为：调度器安排工作，Agent 动手修改，检查器运行考试并交回结果。两道考试都过，调度器才说完成。

## 一次性入口如何兼容

RepairController.run 的函数体保持原样，原 _verify、_regress、_run_check 名字保留为薄适配层，最终调用同一个 VerificationRunner。
已有调用方或测试对 _run_check 的替换仍能生效，检查器通过可信 executor 回调兼容旧挂钩。正常新调用直接使用公开 verify/regress，不需要了解这个兼容细节。
命令参数、退出码分类、错误与超时处理、报告文件名和结果字段保持不变。
